# PRD：get_jobs 扩展 — 高校招聘会采集 + 定向投递 + 简历定制

- 版本：v0.1（草案）
- 日期：2026-11-18
- 基于项目：`loks666/get_jobs`（本仓库为其二次开发版本）
- 目标用户：2027 届计算机相关专业学生（Java 后端 / AI Agent 方向）

---

## 1. 背景与问题

1. **投递渠道单一**：现有系统实际只有 BOSS 直聘一条可用链路（猎聘有导航竞态 bug，51job/智联脚本已失效），而校招的主战场恰恰是高校就业网的双选会/宣讲会。
2. **信息分散**：目标高校的招聘会信息散落在各校就业网、省平台、国家平台，格式不统一，靠人肉每天刷效率极低。
3. **简历一刀切**：目前 BOSS 投递用的是同一张图片简历。Java 后端岗、AI Agent 岗、全栈岗的筛选关键词不同，一份简历命中率有限。
4. **缺少决策依据**：不知道哪场招聘会值得去、去了该找哪几家企业、每家投什么岗位。

## 2. 产品目标

| 目标 | 衡量方式 |
|---|---|
| 招聘会信息一站式聚合 | 覆盖 ≥2 个站点，单次采集 ≥20 场，字段完整率 ≥90% |
| 定向投递有依据 | 每场招聘会输出「目标企业 Top N + 匹配理由 + 缺口」 |
| 简历按岗位定制 | 输入 JD → 60s 内生成定制版，事实零编造，可导出 docx/pdf |
| 不破坏现有能力 | BOSS 投递链路保持可用，新功能独立降级 |

## 3. 用户故事

- 作为求职者，我每天早上能看到未来 7 天苏州/南京/上海目标高校的招聘会，按匹配度排序。
- 我点开一场招聘会，能看到参会企业、在招岗位，并标出哪些适合我、我缺什么。
- 我针对某个 JD 一键生成定制简历，预览确认后导出，投递时自动带上对应版本。
- 我能看到一场招聘会的「作战包」：时间、地点、目标企业、建议简历版本、通勤提示。

## 4. 功能需求

### 4.1 招聘会数据采集（P0）

**采集范围（MVP）**
- 国家大学生就业服务平台（24365）
- 江苏省 91job 智慧就业平台
- 苏州科技大学就业信息网
- 苏州大学就业信息网
- 扩展位：南京/上海目标院校（适配器插拔）

**采集字段**

| 层级 | 字段 |
|---|---|
| 招聘会 | 名称、类型（双选会/宣讲会/线上）、开始/结束时间、地点、城市、主办方、参会企业数、详情链接、来源站点、原始 HTML 存档 |
| 参会企业 | 企业名、行业、规模、在招岗位、学历/专业要求、薪资、投递方式（链接/邮箱/现场） |

**规则**
- 调度：每日 08:00 自动 + 手动刷新；按 `(site_code, event_key)` 幂等去重
- 过滤：目标城市、未来 14 天、关键词（Java / AI / 后端 / 开发 / Agent）
- 合规：单站 ≥3s 请求间隔、只抓公开页面、失败退避、仅个人求职用途
- 容错：单站点失败不影响其他站点；解析失败留存原始 HTML 便于修适配器

### 4.2 匹配与定向投递（P1）

**匹配打分（0–100）**
- 硬条件（不满足直接降权）：学历、专业、届别、城市
- 技能匹配：JD 关键词 ↔ 简历技能图谱（Java、Spring Boot、MyBatis、MySQL、Redis、AI Agent、RAG、Function Calling、Vue…）
- 企业质量：行业、规模、是否目标行业
- 输出：分数 + 命中理由 + 缺口清单

**输出物**
- 招聘会日历/清单（按匹配度、时间排序）
- 单场「作战包」：时间地点、目标企业 Top N、每家匹配岗位、建议简历版本、通勤提示

**投递动作分级（明确边界）**

| 级别 | 场景 | 自动化程度 |
|---|---|---|
| L1 | 有公开投递链接或 HR 邮箱 | 自动生成邮件草稿（附定制简历），**人工确认后发送** |
| L2 | 需登录的校招系统 | 打开页面并预填表单，人工提交 |
| L3 | 现场投递/需报名 | 生成清单与提醒，不自动化 |

**明确不做**：绕过验证码、伪造学生身份、高频批量骚扰。

### 4.3 简历定制（P1）

**第一步：简历结构化（一次性）**
- 解析现有 docx → 结构化 JSON：基本信息 / 教育 / 技能 / 项目 / 实习 / 荣誉
- 建立**事实库**：每条经历有 ID、可追溯；AI 只能重组、改写措辞，**不得新增事实**

**第二步：定制流水线**
1. 输入 JD（粘贴文本 / 链接抓取 / 招聘会企业岗位）
2. JD 解析：必备技能、加分项、职责关键词、隐性偏好
3. 匹配事实库：选择项目、排序技能、决定详略
4. 生成：按 STAR 重写项目描述、量化成果、生成一句话定位
5. **一致性校验**：生成内容必须能在事实库中找到依据，否则打回重写
6. 预览确认 → 导出 docx / pdf → 存为版本并关联岗位

**版本管理**
- `resume_version`：名称、目标岗位、内容 JSON、docx/pdf 路径、使用记录
- 与投递联动：BOSS 图片简历可选择版本（复用 docx→PDF→JPG 管线）

### 4.4 前端

- `/fair`：招聘会日历 + 列表 + 筛选（城市/时间/类型/匹配度）
- `/fair/[id]`：单场详情、参会企业、匹配岗位、作战包
- `/resume`：版本列表、预览、定制向导（JD 输入 → 生成 → 对比 → 确认）
- 现有导航加入口，保持现有 BOSS/配置页面不变

### 4.5 数据模型（新增表）

```sql
fair_site      (id, site_code, name, base_url, adapter, enabled, fetch_interval)
fair_event     (id, site_code, event_key, title, type, start_time, end_time,
                location, city, host, detail_url, company_count, raw_html, created_at, updated_at)
fair_company   (id, event_id, company_name, industry, scale, jobs_json,
                apply_url, apply_email, match_score, match_reason)
resume_fact    (id, category, title, content, tags, start_date, end_date, verified)
resume_version (id, name, target_job, jd_text, content_json, docx_path, pdf_path, created_at)
delivery_task  (id, channel, fair_event_id, company, job, resume_version_id,
                status, result, created_at)
```

## 5. 技术方案

- **后端**：沿用 Spring Boot 3.5 + MyBatis-Plus + SQLite，新增包：
  - `worker/fair/`：`FairSiteAdapter` 接口 + 各站点实现（`NcssAdapter`、`Js91JobAdapter`、`SustAdapter`…）
  - `service/FairMatchService`：匹配打分
  - `service/ResumeTailorService`：JD 解析 + 定制生成 + 一致性校验
  - `application/controller/FairController`、`ResumeController`
- **采集**：复用 PlaywrightManager 的浏览器能力（独立轻量上下文，避免干扰 BOSS 登录态）
- **AI**：复用 `AiService`（DeepSeek，配置已在库中）；新增结构化输出封装（JSON 模式 + 解析失败重试）
- **文档生成**：docx 用 Apache POI（纯 Java，避免额外运行时）；PDF 用 Word COM / LibreOffice headless；JPG 用 PDFBox
- **前端**：Next.js 现有框架新增页面，复用现有 UI 组件
- **调度**：Spring `@Scheduled` 每日采集 + 手动触发接口

## 6. 里程碑

| 阶段 | 内容 | 预估 |
|---|---|---|
| M0 | 脚手架：建表、实体、Controller 骨架、前端路由占位，保证可编译启动 | 0.5 天 |
| M1 | 招聘会采集：2 个站点适配器 + 列表页 + 手动刷新 | 1.5 天 |
| M2 | 匹配打分 + 单场详情/作战包 | 1 天 |
| M3 | 简历结构化 + AI 定制 + 版本管理 + docx/pdf 导出 | 2 天 |
| M4 | 邮件草稿投递 + BOSS 简历版本联动 | 1 天 |
| M5 | 定时调度、日志告警、异常兜底、验收 | 0.5 天 |

合计约 6.5 个工作日（按单线程估算）。建议先做 M0–M2，跑通「采集→匹配→清单」，再上简历定制。

## 7. 验收标准

- [ ] 采集 ≥2 站点、≥20 场招聘会，字段完整率 ≥90%，重复刷新不产生重复数据
- [ ] 匹配打分抽样 20 条，与人工判断一致率 ≥80%
- [ ] 定制简历生成 ≤60s；事实一致性检查 100% 通过（无编造）
- [ ] 导出的 docx 可直接投递，PDF 排版无串行
- [ ] 新功能异常不影响 BOSS 投递主链路

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 各校网站结构差异大、改版频繁 | 适配器隔离；解析失败告警 + 原始 HTML 存档；按站点单独修复 |
| 登录/验证码 | MVP 只做公开页；需登录站点人工登录一次后持久化 Cookie（复用 CookieService） |
| 反爬限流 | 请求间隔 ≥3s、单日一次、失败指数退避 |
| AI 编造经历 | 事实库强约束 + 生成后一致性校验 + 必须人工确认 |
| 招聘会投递闭环有限 | 明确 L1/L2/L3 分级，不承诺全自动 |
| 与现有 BOSS 投递抢占浏览器 | 独立浏览器上下文 + 任务互斥锁 |
